# Security, threat model and observability baseline

Foundation v1 · 2026-10-30. This is an engineering control plan, not a certification, penetration test, legal conclusion or production clearance. There is no deployed mobile/backend system in this repository. Engineering owns implementation; Security reviews materially changed trust boundaries; Founder owns release authorization. Before collecting real data, assign named operational owners and prove the controls below on the actual targets.

## Reference scope and verification

Use the current [OWASP MASVS control groups](https://mas.owasp.org/MASVS/) for mobile and the stable [OWASP ASVS 5.0.0](https://github.com/OWASP/ASVS/tree/v5.0.0) for backend/API requirements. Select applicable requirement IDs and tests in the first implementation's security review; do not claim all controls or a verification level from this family-level mapping. Use [MASTG](https://mas.owasp.org/MASTG/) for mobile test procedures. Recheck versions when implementing; bleeding-edge ASVS content is not this baseline.

| Reference family | Required target control | Evidence before live use / owner |
| --- | --- | --- |
| MASVS-STORAGE / CRYPTO | Keychain for credentials; protected files/database; OS crypto, no embedded master key; minimal sensitive cache and backup exposure | Device storage/backup inspection, locked-device behavior, logout deletion / iOS + Security |
| MASVS-AUTH | Verified server identity/authorization; token expiry/revocation; step-up for destructive/sensitive actions | Expired/revoked/stolen-session, cross-user and recovery abuse tests / Backend |
| MASVS-NETWORK | TLS/ATS defaults, valid host/certificate validation, no cleartext or permissive trust delegates | Interception/invalid certificate tests, endpoint configuration / iOS + Backend |
| MASVS-PLATFORM | Minimum HealthKit/notification permissions, validated deep links, protected background work and sharing | Denied/unavailable/disconnected/locked-device cases; no sample leakage / iOS |
| MASVS-CODE / RESILIENCE | Locked dependencies, input bounds, signed release provenance; assume client can be modified | Supply-chain evidence and forged-client tests; risk-based hardening decision / Engineering |
| MASVS-PRIVACY | Minimize collection, purpose-specific access and documented lifecycle | Inventory, permission UX and export/deletion tests / Product + Privacy |
| ASVS validation / API / business logic | Strict schemas, parameterized queries, idempotency, quotas and server authority | Invalid/oversized/duplicate/replayed requests and state-conflict tests / Backend |
| ASVS authentication / session / authorization | Identity from verified session, ownership per operation, least privilege | IDOR matrix, token lifecycle, admin/entitlement review / Backend + Security |
| ASVS cryptography / secure communications / data protection | Managed keys, encrypted transport/storage/backups, restricted secrets | Configuration inspection, rotation and restore rehearsal / Operations |
| ASVS configuration / secure coding / logging / error handling | Secure defaults, bounded errors, redacted telemetry and incident procedure | Negative log tests, dependency review and incident exercise / Engineering + Operations |

## Mobile and API defaults

Never commit secrets, private keys, signing credentials or production data. Apps cannot keep a server secret: bundle/API keys intended for public clients are constrained by provider policy and never grant administrative authority. Inject server secrets through the eventual environment's secret manager, separate environments, rotate and scope credentials, and keep them out of CI logs/artifacts. CI here has read-only permissions, no app secrets and no deployment.

Store tokens in Keychain with an explicitly reviewed accessibility class and `ThisDeviceOnly` where migration is unnecessary. Prefer access only while unlocked; background HealthKit work may require a narrower, documented after-first-unlock exception. Do not weaken all storage to solve background access. Use Data Protection for sensitive files/database; decide backup exclusion and key recovery by data category. Do not put secrets/health values in UserDefaults, filenames, clipboard, URLs, notifications, screenshots or crash attachments. Redact sensitive app-switcher content where needed; do not cache more than the user-facing purpose requires. Use platform cryptography and provider-managed key rotation, not custom encryption protocols or obfuscation as storage security.

Keep ATS/TLS default validation; no `NSAllowsArbitraryLoads`, trust-all certificate handler or HTTP downgrade. Certificate pinning is a future risk decision requiring rotation/recovery design and tests, not a default checkbox. Bound request/response sizes, timeouts, pagination and decoding. Validate deep-link hosts/routes/parameters and reauthorize sensitive actions; a link never confers identity or entitlement. Restrict WebViews/external URL schemes when they actually exist.

Authentication/provider selection is deferred. A future OAuth/OIDC native flow must use an approved system browser flow, PKCE and state/nonce validation; never collect provider passwords. Access tokens are short-lived and scoped; refresh tokens use secure storage, rotation/reuse detection and revocation as supported by the chosen provider. TTLs are TBD in that contract. Verify signature/issuer/audience/time, key rotation and session status server-side. Handle logout, account compromise and deletion by cancelling tasks, clearing local session state and revoking server sessions; test offline and retry races. Never log tokens or rely on token decode without verification.

Authorize every object/operation from the verified server principal, not a body/path/header `userId`, role, subscription Boolean or device assertion. Test read/write/list/export/delete across two users and admin scopes. Use row/tenant restrictions as defense in depth, no shipped service-role key and no all-powerful database user in ordinary request paths. Separate admin access, require MFA/step-up and time-bounded purpose where supported, audit access and prohibit ad-hoc health-data browsing. Future support tools need explicit authorization and minimization, not inherited broad privilege.

Billing truth comes from server-verified signed transactions/provider notifications, checked for app/environment/account binding, unique transaction/event identity, freshness, refund/revocation and replay. Client StoreKit state is display/cache input, not server authority. Offline entitlement behavior needs a bounded expiry/grace policy reviewed before implementation. Forged coaching requests must not overwrite server history/policy/eligibility or assert clinical clearance; validate schema, provenance, version and action authorization. A deterministic decision hash is an integrity identifier, **not a cryptographic signature or authentication proof**.

Rate limits, per-user quotas, idempotency and bounded retries apply to mutations and expensive operations, including auth, coaching, export and deletion. Limits are TBD until workloads exist. Atomically bind idempotency key to authenticated principal, operation and payload digest; enforce expiry/freshness and reject key reuse with a different request. Signed webhooks require provider verification and deduplication; browser endpoints also need a CSRF/CORS contract if introduced. No new browser auth scheme is selected here.

Assume a rooted/jailbroken or instrumented device can read/alter its client state and fabricate requests. Server authorization, entitlement validation and rate controls remain necessary. [App Attest](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity) is a future risk-based additional signal for sensitive/abused operations: server challenges, freshness/counters, replay handling and unavailable-device/recovery behavior must be designed and tested. It cannot establish user identity or replace authorization. Do not automatically lock users out on a brittle jailbreak heuristic. Obfuscation, anti-debug and tamper controls require demonstrated abuse value and recovery/accessibility review; no such tooling is added now.

## Initial threat model

Assets: identity/sessions, health/training history and derived decisions, entitlement/revenue, admin privileges, source/build integrity and privacy-request outputs. Boundaries: device↔platform store, client↔API, API↔datastore/providers, admin↔data, repository/dependency↔CI and backup↔restore. The table describes target risks; controls are **documented, not implemented**, except repository scans/locks/CI. Residual risk is qualitative and not an accepted production risk.

| Asset | Threat | Attack path | Impact | Controls | Residual risk | Owner / stage |
| --- | --- | --- | --- | --- | --- | --- |
| Account/session | Account takeover | Phishing, credential reuse, stolen refresh token or recovery abuse | Unauthorized data access/changes | Provider security, PKCE, token rotation/revocation, rate limits, reauth for sensitive actions, session monitoring | Compromised user device/provider; recovery social engineering | Backend + Security / before auth activation |
| Health/training history | IDOR / broken authorization | Change object/user ID; unscoped list/search/export | Cross-user disclosure/mutation | Principal-derived scope, operation/field checks, DB isolation, two-user negative tests | New endpoints or admin bypass | Backend / every data endpoint |
| Entitlement | Subscription fraud | Forged client Boolean/receipt, stale signed event, refund/replay | Unpaid access, incorrect revocation | Server provider verification, account/environment binding, deduplication and reconciliation | Provider outage and offline grace abuse | Backend + Billing / before subscription |
| Decision/history authority | Forged coaching request | Submit fake eligibility, policy version or server-owned historical facts | Unauthorized/unsafe decisions or corrupted state | Canonical validation, source authority, policy/version checks, permissions, explicit apply action and audit | Plausible false self-report; domain validation cannot prove truth | Core + Backend + domain authority / before real coaching |
| Sensitive data | Device/network/storage exposure | Lost device, cache/backup dump, permissive TLS or sharing | Health/privacy harm | Keychain/Data Protection, TLS, minimum cache, protected backups, explicit export/sharing | Unlocked compromised endpoint and intentional recipient disclosure | iOS + Operations / before collection |
| Secrets/health values | Log leakage | Request body, exception dump, SDK/crash attachment or URL | Credential exposure and sensitive-data propagation | Allowlist structured fields, safe error mapping, redaction tests, short approved retention, restricted sinks | Misconfigured third-party crash/analytics SDK | Engineering + Privacy / before telemetry |
| Build/runtime | Compromised dependency or action | Malicious update, install hook, mutable action tag or leaked CI token | Source/data exfiltration, compromised build | Exact locks, SHA actions, archive checksums, no lifecycle scripts, review/audit, least CI permissions | Compromised maintainer/registry; scanner misses | Engineering / every dependency change |
| Availability/data integrity | Replay / resource abuse | Repeated mutation/webhook, large payload or expensive decision flood | Duplicate effects, cost/DoS | Principal-bound idempotency, freshness, dedupe, size/concurrency/rate limits and monitoring | Distributed authenticated abuse | Backend + Operations / before public API |
| Sensitive data/admin powers | Admin misuse | Broad support key, shared account, unrestricted query or export | Bulk disclosure or unauthorized changes | Separate least-privilege roles, MFA, purpose-limited access, immutable metadata audit and access review | Privileged insider/collusion | Security + Operations / before admin access |
| Account/export/delete | Privacy-request abuse | Stolen session triggers deletion, guessed export URL, repeat jobs, stale backup restore | Irreversible loss/disclosure or data resurrection | Reauth, principal binding, bounded jobs, expiring one-time exports, deletion ledger/tombstones and restore replay | Reauthenticated compromised account; retained legal exceptions | Backend + Privacy / before account lifecycle |

Update this table when an endpoint/provider/data category/admin capability changes. New material threat requires scoped independent Security review; no need for a new document per PR. Before release, test controls with synthetic data and record remaining risks and owners. Sporting safety review remains separate and cannot be replaced by this threat model.

## Logging, analytics and monitoring

Production logging is an **allowlist** of structured events. Allowed when needed: request/decision/trace IDs, endpoint/action name, schema/policy/app version, duration/count/status and stable error category. Opaque pseudonymous internal identifiers may be used under restricted access with approved retention; they are not automatically anonymous. Prefer aggregate counts; do not hash emails as a substitute for minimization. Decision IDs are correlation metadata, not exported input snapshots.

Prohibited: passwords, secrets, access/refresh tokens, cookies, Authorization headers, raw request/response bodies, raw HealthKit payloads, unnecessary health values, emails, names, phone/address, route coordinates, free text and other PII. Do not stringify arbitrary errors/DTOs/SDK objects. Scrub HTTP URLs/query strings, database exceptions, crash breadcrumbs and analytics properties at source; scrub sinks as defense in depth. Disable default body/header capture and sensitive screen attachments. Notifications show no sensitive workout/health content by default.

Before telemetry activation, define schema allowlist, collection purpose, access roles, deletion/retention and vendor data flows in the inventory. Add negative tests proving forbidden fields/values do not reach test sinks under success, validation failure, provider error and crash paths. CI currently scans source secrets, **not runtime log privacy**. Debug logging uses synthetic local data; production builds cannot enable unrestricted body logging remotely.

Operational monitoring should cover auth failure/rate spikes, authorization denials, entitlement verification failures, queue/retry saturation, API error/latency and export/deletion/backup job failure without logging health content. Set alert thresholds and on-call/escalation owner from real traffic; TBD before launch. Audit security actions separately from diagnostics: actor pseudonymous ID, action, scoped resource ID, timestamp, outcome and correlation ID, never raw prior/new health values. Restrict, integrity-protect and review audit access; choose retention with Privacy/DPO. Audit does not justify indefinite collection.

## Supply chain and repository automation

Automated now: ESLint, actionlint, redacted Gitleaks working tree/history, high/critical npm vulnerability audit for both lockfiles, immutable freeze guards, read-only tokens, pinned official action SHAs, checksum-verified scanners and root npm exact locks. No `pull_request_target`, untrusted PR code with privileged tokens, deploy, signing or secret injection. Monthly Dependabot config covers root npm tooling and GitHub Actions after adoption into the default branch; it deliberately excludes frozen Core updates. Registry audits are time-specific detection, not proof a dependency is safe.

The Gitleaks config extends default rules, with only rule+match+fixed-file exceptions for reviewed historical SHA-256 fields and two synthetic labels. It does not skip entire evidence folders or disable the generic key detector. A credential in the same file remains in scope. Revisit exceptions on scanner upgrade or any authorized fixture change. No live credential is accepted as a baseline.

Manual: review dependency necessity, provenance/maintainer changes, install scripts, licenses/notices, platform privacy manifests and exported transitive license obligations before redistribution. Root tooling is not a published package and this foundation selects no app license. A future license/SBOM tool is justified when a distributable has real dependencies; do not infer license permission from a clean audit. Vulnerable frozen dependencies require an explicitly authorized successor/remediation decision, never an automatic freeze edit.

The repository is public as checked on 2026-10-30. [GitHub documents free public-repository security capabilities](https://docs.github.com/en/code-security/getting-started/github-security-features), including secret scanning and code scanning. Recommended manual settings: verify secret scanning/push protection and Dependabot alerts; enable the `CI` required check when an integration branch is authorized. Do not assume settings were applied by this branch. CodeQL is available for this public context but deferred: current executable source is a frozen reference plus small tooling and extensive copied historical JS, with no production API/app. Evaluate a scoped JS/TS setup when backend source exists (or earlier if a concrete vulnerability justifies it), pin actions and avoid duplicate alert noise; choose Swift/Kotlin analysis only with actual targets. No paid feature is required.

## Incident, backup and recovery minimum

Before live data, name an incident lead and security reporting channel (TBD; do not publish an invented address). A repository vulnerability can be reported through GitHub private vulnerability reporting **if enabled**; avoid public issues containing secrets/health data. Establish triage/escalation and exercise one synthetic scenario before release.

On detection: restrict exposure/disable affected access, revoke/rotate credentials and sessions, preserve minimal restricted forensic metadata, identify affected versions/data/principals, patch with review and verify containment. Assess notification/reporting obligations and timing with legal/DPO under then-current rules; this foundation does not prescribe legal deadlines. Record a factual incident timeline, communicate via the authorized owner, perform recovery verification and add a regression/control improvement. Never copy production payloads into public issues, CI or fixtures.

Backups must be encrypted, access-separated, monitored and retained for an approved period; access to keys and restores is least privilege. Define RPO/RTO and verify a restore into an isolated environment before live dependence. After restore, apply deletion ledger/tombstones and revocation state **before** serving data or rerunning imports, so backups cannot resurrect erased accounts or cancelled permissions. No live-data service, backup job or incident monitor is implemented here.
