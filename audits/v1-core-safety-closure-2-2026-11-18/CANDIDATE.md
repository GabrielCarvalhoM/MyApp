## 4a. New finding (pre-existing; not changed here): CORE-C2-F01, restart sizing reads superseded rows

Found by the successor worker and reproduced by the Chief. It is the same on this tree, on `4c60915` and on `7e03f84` (before E-1); the probe is `probes/restart-superseded-sizing-p14.mjs`, which uses scratch imports.

On `restartProgram` from a stored record that holds a correction, the new plan's run sessions are sized at **60/60/60 min**. The direct merge and the merged control (no superseded rows) give **50/50/50**; the long run is 100 in every case. A correction with no second source does the same ("plain alone"), and taking the superseded rows out of the record gives 50 again. So the restart appears to count replaced rows as training. That is **less conservative** (more prescribed volume than the as-if control), and it is a dose.

This mission forbids dose changes, and the defect predates the line, so it is not fixed. No successor pins it: the restart as-if check covers only what the historical test reads, and a comment in the successor names the gap. **For SSCTR and QRE to rule on: does it block this freeze, or go to the next mission (owner: R6 restart / Core)?**
