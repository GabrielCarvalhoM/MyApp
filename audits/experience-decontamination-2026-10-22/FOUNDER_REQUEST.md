# Pedido direto do Founder — 2026-10-22

Proveniência: pedido do usuário na sessão Codex desta missão, em 2026-10-22, America/Sao_Paulo. Texto abaixo transcrito do pedido atual; a conversa ChatGPT referenciada é contexto importado, não autorização adicional.

Execute uma missão de descontaminação documental e preparação de contexto para o novo Vilumo Fit, preservando todo o cérebro do produto e retirando autoridade da UI/UX antiga sem apagar histórico útil.

OBJETIVO
Preparar o projeto para que, quando o Claude retomar o novo Figma independente, ele conheça profundamente o produto real — Adaptive Engine, Athlete Model, Run Intelligence, Strength Intelligence e demais verdades de domínio — sem ser contaminado por layouts, navegação, decisões visuais ou soluções de UX do Vilumo anterior.

PRINCÍPIO CENTRAL
PRESERVE THE BRAIN. REPLACE THE EXPERIENCE.

Não redesenhe o produto e não altere o novo Figma nesta missão. Esta é uma missão documental/governança para separar claramente Product/Domain Truth de Legacy Experience.

1. REIDRATAÇÃO PROPORCIONAL
Leia apenas as autoridades necessárias para entender:
- arquitetura documental atual;
- quais arquivos são fontes de verdade;
- onde Product/Domain e UI/UX estão misturados;
- estado atual de CURRENT_MISSION e MISSION_LEDGER;
- regras em CLAUDE.md e AGENTS.md.

Não faça broad scan sem necessidade. Respeite Execution Proportionality & Anti-Overengineering.

2. CLASSIFICAR O CONTEÚDO EXISTENTE
Classifique decisões/documentos/regras em três grupos:

A. PRODUCT / DOMAIN TRUTH — CONTINUA AUTORITATIVO
Exemplos:
- Product Thesis / positioning;
- V1 scope;
- Adaptive Engine;
- Athlete Model;
- Run Intelligence;
- Strength Intelligence;
- Recovery / Load / Interference;
- stable-by-default adaptation;
- Minimum Effective Change;
- progression / periodization;
- Run-first / Strength-first / Balanced;
- user agency;
- evidence / epistemic rules;
- planned vs actual;
- wearables;
- subscription/business rules;
- shareability/privacy;
- data semantics.

B. BEHAVIORAL UX PRINCIPLES — CONTINUAM VÁLIDOS SE FOREM INDEPENDENTES DA UI ANTIGA
Exemplos:
- Inspect ≠ Execute;
- progressive disclosure;
- material changes require user agency;
- learning does not imply plan mutation;
- NO INSIGHT IS BETTER THAN A FAKE INSIGHT;
- evidence-aware copy;
- historical continuity;
- planned vs completed distinction;
- external shareability remains V1.

C. LEGACY EXPERIENCE / VISUAL PRESCRIPTION — PERDE AUTORIDADE
Exemplos:
- antiga navegação;
- antiga Home;
- antiga Week;
- layouts;
- composição de cards;
- gradients específicos;
- visual candidates;
- S1;
- Pierre como referência estética;
- screen maps antigos;
- frame-specific instructions;
- decisões de styling;
- qualquer regra que diga COMO o novo Figma deve parecer baseada na UI anterior.

3. NÃO DELETAR DESTRUTIVAMENTE
Não apague histórico útil por padrão.

Quando possível:
- reclassifique;
- marque como SUPERSEDED / LEGACY / ARCHIVE;
- remova da cadeia de autoridade ativa;
- preserve rastreabilidade.

Só remova conteúdo de autoridade viva quando a remoção for necessária para evitar conflito, mantendo histórico quando apropriado.

4. FORMALIZAR A NOVA FRONTEIRA DE AUTORIDADE
Deixe explícita no projeto a separação:

PRODUCT / DOMAIN TRUTH
= o que o Vilumo é, sabe, calcula, decide, permite e quais constraints devem ser verdade.

EXPERIENCE TRUTH
= como o usuário acessa, entende e opera essas capacidades.

O novo Figma independente será o candidato à nova Experience Truth, mas ainda NÃO deve ser declarado final Design Source of Truth antes da reconciliação intelectual e auditoria.

Estado recomendado:
- Figma/UI anterior: LEGACY / SUPERSEDED AS ACTIVE UX AUTHORITY.
- Novo Figma: NEW EXPERIENCE CANDIDATE / ACTIVE DESIGN EXPLORATION.

5. PROTEGER O NOVO FIGMA DE CONTAMINAÇÃO
Formalize guardrails claros para qualquer futuro agente/designer:

THE NEW FIGMA OWNS THE EXPERIENCE ARCHITECTURE.
DOMAIN DOCUMENTS PROVIDE CAPABILITIES, CONSTRAINTS AND TRUTH — NOT LAYOUT.

PRODUCT CAPABILITY DOES NOT IMPLY UI SURFACE.

DO NOT ADD A SURFACE SOLELY BECAUSE A CAPABILITY EXISTS.

NO PIXEL MIGRATION. SEMANTIC MIGRATION ONLY.

DO NOT BEND THE NEW EXPERIENCE TO MATCH THE OLD FIGMA. BEND IT ONLY WHEN REQUIRED BY PRODUCT TRUTH.

6. PREPARAR UM CONTEXTO LIMPO PARA O CLAUDE/DESIGNER
Crie, preferencialmente como visão derivada mínima ou briefing autoritativo enxuto, um contexto UI-agnostic que um designer possa ler antes de continuar o novo Figma.

Esse contexto deve explicar apenas:
- o que o Vilumo é;
- V1 scope;
- proposta de valor;
- Athlete Model;
- Adaptive Engine em termos de capacidades/constraints;
- Run Intelligence;
- Strength Intelligence;
- Recovery / Load / Interference;
- priority hierarchy;
- stable-by-default adaptation;
- user agency;
- evidence/epistemic discipline;
- wearables capabilities;
- shareability/privacy;
- subscription requirements quando relevantes;
- quais dados/estados reais existem.

NÃO incluir:
- layouts antigos;
- screenshots antigos;
- composição de Home antiga;
- screen maps antigos;
- visual candidates;
- styling antigo;
- referência Pierre;
- S1;
- instruções prescritivas sobre cards, gradients, spacing ou estrutura de navegação herdada.

7. NÃO TRANSFORMAR O BRIEF EM NOVO CONTRATO GIGANTE
O briefing deve ser apenas o suficiente para um designer entender a profundidade do produto sem herdar a solução anterior.

Se as autoridades atuais já permitirem gerar isso dinamicamente sem novo documento, prefira atualizar índices/authority maps em vez de criar documentação redundante.

8. AUDITAR CLAIMS E CAPACIDADES QUE O NOVO FIGMA PROVAVELMENTE VAI CONSUMIR
Sem editar o Figma, identifique pontos que exigirão rigor quando o designer voltar, por exemplo:
- readiness / prontidão;
- cardio / pernas / upper scores;
- interference claims;
- estimated strength;
- ideal/planned volume ranges;
- progress claims;
- recovery language;
- athlete learning language.

Não redesenhe nada. Apenas garanta que o futuro designer terá acesso à verdade e às limitações corretas.

9. ATUALIZAR AUTORIDADES MÍNIMAS
Atualize apenas os documentos necessários para:
- retirar autoridade da UI/UX antiga;
- preservar princípios comportamentais válidos;
- definir a fronteira Product Truth vs Experience Truth;
- registrar o status dos dois Figmas;
- preparar reidratação limpa futura.

Evite criar um segundo conjunto de verdades.

10. NÃO FAZER NESTA MISSÃO
Não:
- alterar o novo Figma;
- redesenhar telas;
- comparar visualmente os dois Figmas;
- sincronizar telas antigas com novas;
- adicionar features;
- reabrir discovery;
- reabrir o Adaptive Engine;
- reescrever toda a documentação;
- apagar histórico útil;
- transformar documentação de domínio em especificação visual.

11. DEFINIÇÃO DE PRONTO
A missão está pronta quando:
- Product/Domain Truth continua intacto e autoritativo;
- UI/UX antiga não influencia mais automaticamente futuros agentes;
- princípios comportamentais válidos foram preservados;
- conteúdo visual antigo está claramente superseded/legacy;
- o novo Figma está formalizado como candidate, ainda não como fonte final;
- existe um caminho claro de reidratação para o Claude conhecer o cérebro do produto sem ver o rosto antigo;
- não há conflito de autoridade entre os dois designs;
- nenhum conhecimento importante de Adaptive Engine/Athlete Model/Run/Strength foi perdido.

12. ENTREGA FINAL
Reporte:
- quais documentos foram alterados;
- quais referências perderam autoridade;
- quais princípios de UX foram preservados;
- qual é agora a hierarchy of authority;
- como o novo Figma está classificado;
- como o antigo Figma está classificado;
- qual contexto o Claude deverá ler quando voltar;
- qualquer ambiguidade ou conflito restante;
- confirmação explícita de que nenhuma solução visual nova foi imposta.

Objetivo final:
CLAUDE SHOULD KNOW THE BRAIN OF VILUMO WITHOUT INHERITING ITS OLD FACE.
