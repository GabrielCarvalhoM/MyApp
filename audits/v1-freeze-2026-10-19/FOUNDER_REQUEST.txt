6. GOAL HIERARCHY — PRIORIDADE ENTRE ESPORTES
==================================================

Formalize uma hierarquia explícita de objetivos.

O sistema precisa saber qual modalidade deve receber prioridade quando existe conflito real.

No onboarding, o usuário deve conseguir declarar algo equivalente a:

- RUN-FIRST;
- STRENGTH-FIRST;
- BALANCED / HYBRID.

Não necessariamente com esses termos expostos literalmente ao usuário.

A UX deve encontrar a linguagem mais natural.

RUN-FIRST:
corrida é prioridade principal; força pode atuar como complementar ou secundária.

STRENGTH-FIRST:
força/hipertrofia/performance de força recebe prioridade; corrida permanece presente, mas não deve sabotar o objetivo primário.

BALANCED:
o usuário deseja desenvolvimento sério dos dois, e o Adaptive Engine deve buscar compromisso explícito.

Além da prioridade, preservar objetivo concreto por modalidade.

Exemplos corrida:

- condicionamento;
- 5K;
- 10K;
- meia maratona;
- maratona;
- melhorar performance;
- base.

Exemplos força:

- hipertrofia;
- força;
- performance;
- fortalecimento complementar;
- manutenção.

O Interference/Adaptive Engine deve usar essa hierarquia para arbitrar conflitos.

Não pode existir arbitragem multiesporte sem prioridade de objetivo.

==================================================
7. SPECIALIST PARITY + CROSS-SPORT SUPERIORITY
==================================================

Preservar integralmente o princípio:

SPECIALIST PARITY + CROSS-SPORT SUPERIORITY.

Run Intelligence:
deve pensar como especialista em corrida.

Strength Intelligence:
deve pensar como especialista em força.

Adaptive Engine:
deve pensar no atleta inteiro e coordenar as modalidades.

O Adaptive Engine não substitui especialização interna.

Objetivo:

- corrida: competência comparável aos melhores produtos especialistas;
- força: competência comparável aos melhores produtos especialistas;
- multiesporte: superioridade potencial através de coordenação, interferência, carga e recuperação.

Isso é target de produto sujeito a validação real.

Não declarar automaticamente que já foi atingido.

==================================================
8. FIRST VALUE / AHA MOMENT
==================================================

Formalize o primeiro momento de valor da V1.

O onboarding NÃO deve terminar em:

“Bem-vindo ao Vilumo.”

Deve terminar em algo próximo de:

“Seu plano está pronto.”

Fluxo conceitual:

Onboarding
→ objetivo
→ prioridade esportiva
→ experiência
→ disponibilidade
→ restrições/equipamentos
→ dados relevantes
→ Athlete Model inicial
→ Run + Strength reasoning
→ geração da semana
→ explicação clara.

O primeiro AHA MOMENT deve ser perceber que:

o Vilumo não apenas colocou um treino de corrida e uma ficha de musculação lado a lado.

Ele coordenou os dois.

Exemplo conceitual:

“Coloquei seu Lower na quinta porque terça é sua sessão-chave de corrida e sábado é seu longão.”

A interface não precisa expor a complexidade inteira.

Mas deve conseguir mostrar o suficiente para o usuário entender:

“há inteligência real coordenando minha semana.”

==================================================
10. STABLE-BY-DEFAULT ADAPTATION
==================================================

Formalize como invariant:

STABLE-BY-DEFAULT ADAPTATION.

Princípio:

“Plan well first. Adapt only when necessary. When adapting, make the smallest change capable of restoring plan quality.”

Após um treino concluído, o comportamento padrão NÃO é alterar o treino seguinte.

O comportamento padrão é aprender.

Adaptação é exceção fundamentada.

==================================================
11. LEARNING ≠ PLAN MUTATION
==================================================

Formalize explicitamente:

Athlete Model Update
≠
Plan Mutation.

Após cada sessão:

1. coletar evidências;
2. atualizar Athlete Model;
3. atualizar estado fisiológico/performance relevante;
4. verificar o impacto no restante da semana;
5. perguntar se o plano ainda permanece dentro de uma faixa aceitável;
6. se SIM → preservar plano;
7. se NÃO → encontrar a menor adaptação eficaz.

O motor deve conseguir concluir frequentemente:

“Aprendi algo novo, mas não existe razão suficiente para mudar seu plano.”

Isso é comportamento desejado.

==================================================
12. PLAN STABILITY COMO CUSTO DE OTIMIZAÇÃO
==================================================

O Adaptive Engine não deve buscar apenas:

“qual seria a prescrição fisiologicamente ótima neste exato momento?”

Ele deve considerar simultaneamente:

- qualidade fisiológica;
- objetivo;
- interferência;
- recuperação;
- risco;
- aderência;
- disponibilidade;
- proximidade temporal;
- confiança já depositada pelo usuário;
- custo de alterar algo já planejado.

Introduzir conceitualmente:

PLAN STABILITY COST / CHANGE COST.

Uma pequena melhora teórica não justifica quebrar planejamento.

O benefício esperado da mudança deve superar um threshold relevante.

Não inventar números arbitrários sem base.

Definir o contrato de decisão.

==================================================
13. MINIMUM EFFECTIVE CHANGE
==================================================

Formalize:

MINIMUM EFFECTIVE CHANGE.

Quando uma adaptação for necessária, buscar a menor intervenção capaz de restaurar qualidade suficiente.

Hierarquia conceitual:

LEVEL 0
learn only / no plan change

LEVEL 1
micro-adjust parameter

LEVEL 2
adjust volume/intensity

LEVEL 3
move one session

LEVEL 4
substitute session

LEVEL 5
partial replanning

LEVEL 6
significant replanning

Sempre avaliar Level 0 primeiro.

Não transformar essa enumeração em estrutura rígida se a arquitetura existente possuir representação melhor.

Preservar a semântica.

Significant replanning deve ser raro.

==================================================
14. HYSTERESIS / NOISE RESISTANCE
==================================================

Formalize resistência a ruído.

O motor não deve reagir exageradamente a pequenas oscilações em:

- RPE;
- pace;
- FC;
- sono;
- sensação subjetiva;
- uma série isolada;
- pequena queda de performance;
- pequena melhora de performance.

Treinamento humano possui variabilidade natural.

Pequena oscilação não deve causar alteração automática.

A adaptação precisa de evidência suficientemente relevante.

Implementar o princípio de hysteresis/decision inertia conceitualmente, sem inventar thresholds médicos ou fisiológicos arbitrários.

==================================================
15. NEXT-WORKOUT STICKINESS
==================================================

Quanto mais próxima estiver uma sessão, maior a preferência por preservá-la.

Formalize:

“TOMORROW’S WORKOUT SHOULD BE STICKY.”

Se o usuário já viu:

Intervals
6 × 800 m
amanhã

isso não deve mudar por qualquer pequena nova evidência.

Sessões próximas exigem razão mais forte para alteração.

==================================================
16. USER AGENCY
==================================================

O Vilumo é treinador, não ditador de calendário.

Quando ocorrer alteração material, o usuário deve manter capacidade de agência.

Conceitualmente, disponibilizar ações simples como:

- aceitar ajuste;
- manter plano atual;
- ver motivo.

A nomenclatura final será resolvida em UX/UI.

Se o usuário rejeitar a alteração:

o motor deve considerar isso como nova restrição e buscar a melhor solução possível dentro dela.

Não transformar isso em painel de configuração complexo.

==================================================
17. EXPLAINABILITY OF MATERIAL CHANGES
==================================================

Quando houver mudança relevante, o Vilumo deve conseguir explicar:

- o que mudou;
- por que mudou;
- qual evidência relevante motivou;
- qual objetivo está sendo protegido.

Evitar mensagens como:

“Otimizamos seu plano novamente.”

Isso sugere que o plano anterior era ruim.

Preferir comunicação factual e calma.

Exemplo conceitual:

“Reduzi uma repetição do treino de intervalos porque seu treino de força gerou carga de pernas significativamente maior que a prevista. O estímulo principal foi preservado.”

Mudanças não devem parecer eventos promocionais.

Elas devem parecer exceções justificadas.

PROGRESSIVE DEPTH.

19. ANALYTICS — TRÊS CAMADAS
==================================================

Formalize a arquitetura UX de analytics em três níveis.

----------------------
LEVEL 1 — ORIENTATION
----------------------

Superfície clean.

Exemplos:

- corrida evoluindo;
- força evoluindo;
- carga semanal adequada;
- consistência;
- principal insight.

Poucos dados.

Alta legibilidade.

----------------------
LEVEL 2 — PROGRESS
----------------------

Área dedicada à evolução.

Estrutura conceitual:

- Running;
- Strength;
- Overall / Multisport.

Cards, tendências e comparações relevantes.

----------------------
LEVEL 3 — DEEP DIVE
----------------------

Profundidade para atletas interessados.

RUN ANALYTICS, quando suportado por dados confiáveis:

- volume;
- frequência;
- pace;
- RPE;
- FC;
- zonas;
- distribuição de intensidade;
- longões;
- sessões-chave;
- aderência;
- capacidade;
- carga;
- tendências;
- histórico;
- ciclos;
- comparação entre períodos;
- resposta ao treinamento.

STRENGTH ANALYTICS:

- séries;
- reps;
- carga;
- volume;
- RIR/RPE;
- PR;
- progressão;
- volume por grupo muscular;
- frequência;
- performance por exercício;
- tendência de força;
- recuperação;
- aderência;
- histórico.

MULTISPORT:

- carga combinada;
- consistência;
- distribuição semanal;
- impacto entre modalidades;
- interferência;
- relação corrida × força;
- recuperação;
- aderência ao plano híbrido.

Não inventar precisão falsa.

Não mostrar inferências como fatos quando não houver evidência suficiente.
